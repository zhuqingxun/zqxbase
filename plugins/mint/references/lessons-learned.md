### 0.3 使用约定

1. **Architect 第一轮扫描**：启动时用本表中每个"权威正字"的**拼音**在全文做模糊匹配，发现任何同音近字变体必须归一。
2. **Worker 执行替换**：在分配的块内，对本表所有权威正字做双向检查（错字→正字 + 正字周围是否有变体残留）。
3. **Reviewer 审查**：批发 Worker 输出前，用本表做最后一轮扫描，发现遗漏立即反馈。
4. **本表维护**：每次 sync 发现新的 ASR 变体，追加到对应"已知 ASR 变体"列；发现新的权威术语（本表未收录），创建新行。**禁止**在本表出现"需人工确认"的模糊态——模糊的条目属于第一章。
5. **人名盲区兜底**：**如果发现疑似人名但不在本表中**，立即列为高优先级 clarification 项让用户确认，不要 AI 自行判断。

## 二、语义陷阱（AI 容易误判）

以下情况 AI 容易做出错误判断，需特别注意：

### 2.1 岗位级别 vs 个人职级
- "做的是22级的岗" ≠ 个人职级是22级
- ASR 口水稿中说"我做的是X级的岗"指岗位级别，个人职级可能更低
- **教训来源**：Architect 将"做的是22级的岗"误读为个人职级22级，错误传播到所有版本

### 2.2 人名同音混淆
- 同一人可能被 ASR 识别为多种写法（如 泽哥/某主管/泽泽 → 同一人"某主管"）
- **必须列为人工澄清项**，不要 AI 自行判断
- 某高级主管/宋三总/孙三总 → 可能是同一人也可能不是，需用户确认

### 2.3 "趋应为"类表达
- ASR 产出的四字词不一定是成语，可能是口语断句被连在一起
- 不要强行匹配成语（如"趋之若鹜"语义方向完全错误）
- **优先按语境理解**，不确定时列为人工澄清项

### 2.4 敏感级别信息
- 职级数字（如20级、21级、22级）属于敏感信息
- 脱敏稿中需移除所有个人/岗位职级数字
- 任职资格等级（如4级、5级）属于制度级别，非个人敏感信息，可保留

### 2.5 级别后缀 "N+" / "B+" 的 ASR 陷阱（2026-04-09 梁毅访谈沉淀）

华为内部有一种级别表达方式：`<级别数字>+` 读作 `<数字> jiā`,表示"N 级及以上"或"B 及以上"。

| 口语表达 | 正确写法 | 含义 |
|---------|---------|------|
| 十九家干部 | 19+ 干部 | 19 级及以上干部 |
| 二十二家干部 | 22+ 干部 | 22 级及以上干部 |
| 考评 B 家 | 考评 B+ | 考评 B 级及以上 |

**ASR 行为**：`jiā` 音节几乎总被识别为中文"家"字。

**校对规则**：遇到"<数字>家 + 干部/级/专家/岗"或"<字母 A-D> 家 + 考评/等级/绩效"的搭配,必须识别为 N+/字母+。

**正则提示**：`(\d{2})\s*家(?=干部|级|专家|岗)` → `$1+` ； `([A-D])\s*家(?=考评|等级|绩效|分)` → `$1+`

**用户原话**："19+ (19级及以上的意思),系统中很多语音识别,可能都会识别到 jia 这个发音,比如我们说 22 jiā 干部,就是 22 级及以上干部,写成 22+。我们会说考评 B jiā,写作 B+"

### 2.6 领域概念借用的 ASR 陷阱（2026-04-09 梁毅访谈沉淀）

华为管理文化中**大量借用物理学/军事/农业等领域的概念**作为管理术语。这类术语在 ASR 中经常被同音字替换,语法完全通顺但语义对不上。

| ASR 误识别 | 正确写法 | 原始学科 | 管理含义 |
|-----------|---------|---------|---------|
| 商增 / 商检 / 商检管理 | 熵增 / 熵减 / 熵减管理 | 物理学（热力学第二定律）| 组织僵化/激活团队 |
| 杀你机器 | 杀你祭旗 | 古代军事 | 问责主官 |
| 一个代际四季 | 一个代际 4G | 无线通信代际 | 一次技术换代 |
| 拦河网 | 拦河网 | 渔业 | 全方位考察 |

**校对规则**：
- 遇到语法通顺但上下文违和的 4 字词,优先考虑**管理类概念 + 借用源**的组合
- "熵"是华为高频管理概念,遇到"商 + 名词"搭配优先尝试"熵 + 名词"
- "4G/5G 等通信代际"在访谈中可能被识别为"四季/五季"（ICT 领域访谈专属陷阱）
- 军事比喻（祭旗、压阵、老将、新兵、死守、突围）常见于一线问责语境

**用户原话**："'熵减',这是借用物理学的概念,用在企业管理中,表示对团队的激活" ；"一个代际 4G 没打好（4G 是无线通信的代际）,后面是'杀你祭旗'"

### 2.7 变革项目/流程简称陷阱（2026-04-09 梁毅访谈沉淀）

华为内部有大量以**动词短语开头**的变革项目/流程（如"合同在代表处审结""一线呼唤炮火""让听得见炮火的人做决策"）,其口语简称常被 ASR 误识别为人名或无意义词。

| ASR 误识别 | 正确简称 | 完整项目名 |
|-----------|---------|-----------|
| 沈杰代表处 / 神杰代表处 | 审结代表处 | "合同在代表处审结"项目覆盖的代表处 |

**校对规则**：
- 遇到"动作+代表处/岗位/主管"类搭配,如果动词部分听起来像人名（沈/审/申同音）,优先考虑变革项目简称
- 此类概念通常由 Architect 在上下文指南中预警,或由用户在阶段 1.5 澄清后加入术语表
- 遇到未知的"X代表处""X代表"模式,不要直接猜人名,列为人工澄清项

**用户原话**："'沈杰代表处'是'审结代表处',这个说法是'合同在代表处审结工作所覆盖的代表处'的简称...'合同在代表处审结'是公司的一个变革项目,核心目标就是商业不用回到集团才闭环,是在代表处就闭环了（审结了）。**这是一个重要概念,加到校对知识库中**"

### 2.8 连音伪成语陷阱（2026-04-09 梁毅访谈沉淀）

ASR 经常将**重复动词 + 虚词**的连续口语（如"杀掉杀掉就""拉出来拉出来就"）误识别为 4 字伪成语（如"沙雕沙雕剧"）。

**识别特征**：
- 看似 4 字词但完全不符合任何已知成语
- 上下文是动作重复+导向强调（如"杀掉也是一种导向""拉出来也是一种威慑"）
- 语法上可读为 SVO 但语义荒谬

**校对规则**：
- **禁止**强行匹配成语（"沙雕沙雕剧"误匹配为"杀鸡儆猴"是方向错误）
- 听起来重复的音节（如"沙雕沙雕""对对对""嗯嗯嗯"）应识别为口语重复,而非正式词汇
- 列为高优先级人工澄清项

**案例**：
- 原文"有没有把主要的主管拉出来？嗯。沙雕沙雕剧嗯。也是一种导向啊"
- 错误 AI 猜测：杀鸡儆猴 / 沙盘推演 / 整顿纪律
- 正确修正：杀掉,杀掉就也是一种导向（ASR 把"杀掉杀掉就"连音识别为"沙雕沙雕剧"）

### 2.9 岗位链完整性检查（2026-04-09 梁毅访谈沉淀）

华为问责话语经常出现**岗位链**,即按层级/职能依次列举主管岗位（如"杀 PD 的、杀 SPDT 的、杀 AD 的、杀代表的、杀大 T 部长"）。岗位链中任何一个环节的缩写被 ASR 误识别,通常可以通过**前后岗位的规律性**推断。

**校对规则**：
- 遇到"杀 X 的、杀 Y 的、杀 Z 的"连续问责句式,所有 X/Y/Z 必须都是岗位名/缩写
- 中间出现中文普通词（如"大题部长""大体系部长"）通常是岗位缩写失真
- 通过**前后岗位缩写的规律**定位未知项（如 PD → SPDT → AD → 代表 → 大 T 部长,DPD 不在这个序列里,应为 SPDT）

**校对启示**：华为岗位链（项目/产品/市场方向）包括但不限于：
- 产品侧：PD → SPDT → PDT
- 销售侧：AD → 代表 → 办事处主任 → 地区部总裁（地总）
- 客户侧：客户经理 → 大 T 部长（Top customer 部长,大客户部长）
- 研发侧：工程师 → SPE → SPDT → PE

**用户原话**："PD/SPDT/AD/代表/大 T 部长,这几个都是公司的主管岗位"

### 2.10 "function" 的中英混合 ASR 失真（2026-04-09 梁毅访谈沉淀）

华为 HR 讨论中 `function HR`（职能 HR）是高频英文术语,ASR 对 `function` 这个单词有多种严重失真：

| ASR 误识别 | 正确 |
|-----------|------|
| 方式来 HR | function HR |
| 翻不着 HR | function HR |
| 戴老师（代表处语境）| 代表处 |
| 代保书反不啥一啥 | 代表处 function 还不行 |
| 方式来查 | function 化 |

**校对规则**：
- 任何涉及代表处 HR 赋能的段落中,遇到"方式/翻/戴/代保"等不自然的中文片段,优先考虑 `function` 失真
- `function HR` 是固定搭配,单独出现的"方式 HR""职能 HR"也可以合并到这个概念
- 此类陷阱**密集出现**在讨论代表处 HR 的整段（如梁毅 00:46-00:50）,Worker 需对整段保持高警觉

### 2.11 整段简化的编辑决策（2026-04-09 梁毅访谈沉淀）

ASR 严重失真时,用户有时不会提供逐字修正,而是直接给出"整段简化"的编辑决策。Worker 应学会识别并应用这类指导。

**案例**：
- 原文（混杂 SABD / VVI / 顾王 / 疏通等多处失真）：
  > "你还记不记得前几年王胜清在嘟做这个这个 S A B D 总裁的时候,当时写过一个报告,嗯,直接引发了公司把一个产品线总裁拿下...嗯,是什么V V I 是疏通的疏通的东西吗？网络啊网络的东西。对啊,你想想吧。这个整个顾王的产品线总裁。"
- 用户指示：**整段简化**为
  > "王胜清当时写过一个报告,直接引发了公司把一个产品线总裁拿下,固网的产品线总裁"

**校对规则**：
- 一段内出现**多处严重失真**（≥3 处）且互相关联时,优先考虑整段重构而非逐字修正
- 重构原则：保留核心事实,删除所有疑似失真的形容/插话/重复
- 如果 Worker 不敢重构,可标记为高优先级澄清项由 Reviewer/Leader 决策

## 三、脱敏规则

### 脱敏范围（需处理）
- 受访者姓名 → "某某业务组织资深员工"
- 受访者岗位、职级 → 移除
- 受访者个人经历细节（如"在终端干了四五年"）→ 模糊化或移除
- 时间戳 → 移除（脱敏稿不含时间点信息）
- **业务归属暗示**（2026-04-08 新增·李红波案例）：改写类文本（观点/摘要/分析）中任何"主语是受访者 + 谓语是业务管理动作 + 宾语是具体业务/产品/系统名"的表达。典型反例："以**他负责的**周边访谈报告为例""**他将**松绑权给予 AT""**他主导的**对口制度改革"。处理方式：
  - 去掉"他负责的/他主导的"等所有权限定词，让业务名变成中立的讨论对象（"以周边访谈报告为例"）
  - 将主动语态改为被动/无主句（"现在已将松绑权给予 AT"）
  - 若必须保留动作主语，改为"业务团队"等模糊集合
  - **注意**：此规则只适用于 AI 改写的观点/摘要文本，原声引用保持原话不改（原声保真是更高优先级规则）
  - **原因**：结合业务名可以反推身份。registry 中每个受访者都有独特的"负责业务"字段，一旦改写文本中出现"他负责的 XX"，等同于直接点名。跨受访者汇总分析时尤其危险。

- **第一人称身份视角泄露**（2026-04-09 新增·迟冉案例）：改写类文本（观点/摘要/分析）中任何"我/我们部门 + 做 + 具体业务名"的第一人称表达。典型反例：
  - "我之前做干部任期制，又做管理者任职资格" → "以干部任期制、管理者任职资格这类从零到一的政策变革为例"
  - "我现在做任职资格" → "在任职资格工作中" 或 "以任职资格为例"
  - "就是学发呀，就是我们这个部门" → "明确指向学发模块"（去除"我们这个部门"）
  - "我做干部专业化，针对…" → "干部专业化维度下，针对…"
  - "光做任职资格的部门，公司就有两个，我是他的子级" → "公司层面存在两个任职资格部门，某业务组织这部分是 CHR 全员任职资格的子级"
  - "原来我来某业务组织比较早" → "某业务组织早期"（去除"我来"视角）
  - "我们每年做 MFP" → "每年一次的 MFP 数据"

  处理原则：
  - 观点段中凡是"我/我们 + 做/负责/主导/推动 + 具体业务名"的组合必须改写为无主句或集体视角
  - **原声段中原则上可以保留**（原声保真），但 Leader 选取原声时应**主动避开**第一人称 + 业务名的句子，优先选其他有代表性的原声
  - 若必须引用含第一人称视角的原声，用 `[...]` 省略身份暴露部分（如"[...]我跟每个 L3、每个 L4 都有关系，每天都好多人找"）
  - **原因**：第一人称比第三人称更直接指向身份。Leader 的脱敏自检往往只扫第三人称动词（"他负责/她主导"），容易漏掉第一人称视角的暴露。本规则针对这一盲区。

- **身份线索的组合反推**（2026-04-09 新增·迟冉案例）：单看一句话可能看不出身份，但**多条信息的组合**可以精确反推受访者身份。Leader 在脱敏稿成稿后应做一次"组合反推测试"：
  - 把观点段和原声段中所有与"负责业务/资历/部门/经历"相关的信息片段抽出来
  - 问自己：如果我是外部读者，看到这些信息的组合，能精确定位到具体哪位受访者吗？
  - 如果能：说明组合信息过于独特，需要进一步模糊化
  - 典型反例：「受访者在学发部门 + 曾做过任期制和任职资格 + 是 CHR 任职资格的子级 + 在某业务组织资历较深」— 这组信息可以直接定位到 registry 中唯一一位受访者
  - 处理方式：保留核心观点，模糊化身份线索（删除或改写个别线索项，不要保留完整组合）

### 扩展扫描模式库（2026-04-09 新增）

基于李红波案例 + 迟冉案例，脱敏扫描模式库扩展为 7 类：

```bash
# 1. 姓名（全名 + 单字拆分）
grep -E '{全名}|{姓}|{名}' {脱敏稿}

# 2. 时间戳（三种格式）
grep -oE '[0-9]{2}:[0-9]{2}:[0-9]{2}' {脱敏稿}
grep -oE '（[0-9]{2}:[0-9]{2}:[0-9]{2}）' {脱敏稿}
```

所有模式**仅扫描观点段**（AI 改写的文本），**原声段不扫**（原声保真）。扫描前应先从脱敏稿中提取观点段内容（例如 `awk '/\*\*观点：\*\*/,/\*\*关键原声：\*\*/'`）。

### 文件名脱敏
- 脱敏版文件名中的受访者姓名替换为代号（如 `受访者_01`、`受访者_02`...）
- 代号由全局注册表（`desensitization_registry.yaml`，位于工作目录上级）统一分配，跨项目唯一
- 各项目 `meta.yaml` 的 `desensitization.name_map` 存储本项目的映射副本
- 示例：`张三_校对稿_脱敏.md` → `受访者_01_校对稿_脱敏.md`

### 保留范围（不脱敏）
- 文中提及的其他人名（非受访者的第三方人名）→ 保留
- 组织名称（某业务组织、CHR 等）→ 保留
- 制度级别（4级/5级任职资格）→ 保留

## 四、结构化分析经验

### 4.1 原声选取
- 原声必须是受访者的话，不是访谈者的话（曾有 Worker 混淆）
- 选最有冲击力的表达：比喻（"清水衙门""断头路""赛道"）、反问、直言批评
- 2-5 条即可，不必覆盖所有细节
- 脱敏版的校对稿和结构化分析中，原声引用不带时间戳。精华原声文件不生成脱敏版

### 4.2 观点归类
- 受访者回答经常跳跃——回答问题 3 时可能带出问题 1 的内容
- 需要全文通读后按主题归类，不能只看时间顺序

## 五、适度模式的精简深度校准（访谈场景）

来源：曹朝勋访谈人工修订 diff（v1 49,808 字 → 人工 30,107 字，删减 40%）。此章节记录适度模式**容易精简不足**的几个典型模式，供 Architect 在上下文指南中提醒、Reviewer 在审查时检查。

### 5.1 访谈者话语分级的实战案例

这次 diff 显示大量访谈者话语被删除。实际删除比例按类型：

| 访谈者话语类型 | 人工删除率 | 典型案例 |
|--------------|-----------|---------|
| A 类提问/追问 | 0% | "好，我们第二个问题..." "你从未来看这个问题的风险" |
| B 类转述 | ~70% | "就是说你要..." "也就是说..." "我理解一下你刚才说的..." |
| C 类短促回应 | ~95% | "对" "就是" "是吧" "嗯" "哎呀，我操" "就是有明确的评价标准" |
| 访谈者的感叹/情绪 | ~100% | "哎呀，我觉得这个东西都可以作为监事会" "我觉得这个观点很有价值" |

**校对启示**：Worker 对访谈者话语应默认偏激进删除，除非明确携带新信息或切换话题。

### 5.2 跨说话人段落合并的典型模式

diff 中最突出的模式：受访者 + 访谈者短回应 + 受访者 → 合并成一段受访者。

示例：
```
原文（v1）:
00:02:00 曹朝勋 ...就像我们做项目交付就数站点。
00:02:10 访谈者 就是有明确的评价标准。
00:02:13 曹朝勋 今天搞十个站点，十个站点搞完大家再去撤...

人工修订:
00:02:00 曹朝勋 ...就像我们做项目交付就数站点。今天搞十个站点，十个站点搞完大家再去撤...
```

这次 diff 中此类合并出现了 30+ 次。Worker 必须掌握此规则。

### 5.3 受访者话题内重复观点去重

受访者经常用三种不同措辞反复说同一观点。人工修订倾向于保留最精炼的一次。

示例：v1 中曹朝勋反复强调"这平台已经允许打 B 的人在那干了"的概念出现 3 次，人工修订只保留 1 次。

**校对启示**：Worker 在适度模式下可以合并受访者对同一观点的多次表达，保留最清晰的一次。但这个操作风险较高，需配合上下文判断是否真的是同一观点。

### 5.4 粗口处理的实际尺度

v1 中保留了约 15 处"他妈的""我操"，人工修订删除了 13 处，只保留 2 处（都是用作数量强调的"他妈的十几个"）。

**校对启示**：适度模式下，粗口的默认动作是**删除**，保留是例外。Worker 原来的"保留语气强化粗口"规则应收紧为"仅在极少数情况下保留"。

### 5.5 访谈者感叹和元评论的删除

人工修订 100% 删除了访谈者的感叹和元评论，如：
- "哎呀，我觉得这个东西都可以作为监事会..."
- "我觉得非常好"
- "你这个洞察很关键"
- "我觉得我们今天这个讨论非常有价值"

这类"元评论"对访谈内容没有增益，反而稀释了受访者的核心观点。

**校对启示**：访谈者的感叹和元评论默认删除。

### 5.6 李红波访谈数据点补充（2026-04-08）

来源：李红波访谈人工修订 diff（v1 33,249 字符 → 人工 19,083 字符，**删减 42%**）。再次验证曹朝勋案例的规则具有普适性，并新增两个数据点。

#### 5.6.1 删减比例对照

两次访谈的删减比例相当（曹朝勋 40% vs 李红波 42%），说明 mint:refine moderate 模式在访谈场景中**系统性地精简不足**，Worker 应将目标删减率从当前的 ~15% 上调至 **35-45%**。

#### 5.6.2 新模式：访谈开场提纲铺陈段应默认删除

李红波访谈开场约 110 字是访谈者介绍研究方法的铺陈（"他上次跟我讲，让我以蓝军视角，因为我是外部的嘛，大家讲起来可能会多一点。另外就是只谈问题，不要讲功劳什么的。他还说你给我的时候不要有任何人名..."）。

这段内容：
- 非受访者观点，属于方法说明
- 对读者理解访谈内容没有增益
- 可能含敏感信息（研究方法/外部身份声明）

**人工修订直接删除，只保留"第一个问题是这样..."的切入**。

**校对启示**：访谈开场的元信息段（研究背景、方法声明、保密约定）应**默认删除**，与 5.5 的元评论规则一致。

#### 5.6.3 新模式：闲聊插入段 100% 删除

李红波访谈中出现三段闲聊插入：
1. **监事会八卦**（v1 第 75-123 行约 50 行）：喝水间隙聊监事会选举、吕总退休、刘总身体状况、刘总工作风格
2. **价值观岔开**（v1 第 359-371 行约 13 行）：访谈者"岔开一下"插入自己的经历感慨
3. **结构化裁员延伸**（v1 第 226-263 行约 38 行）：访谈者长篇补充 CT 产品线裁员的业务例子

**人工修订 100% 删除这三段**。特征：
- 以"喝点水/岔开一下/我岔开一点"等口语过渡词开头
- 内容偏离当前问题主题
- 访谈者主导表达

**校对启示**：Worker 识别到"喝点水""岔开""插一句"等切换信号后的段落，应评估是否属于主题外闲聊，若是则默认删除。

#### 5.6.4 跨说话人合并模式再次大量验证

李红波访谈中跨说话人合并出现 **15+ 次**，与曹朝勋访谈的 30+ 次相当密集。典型例子：

```
原文（v1）:
红波总 00:01:56 你呈现上来的，长的短的，基本上是这么选出来的，对吧？
访谈者 00:02:06 这个最后可能空间就已经不大了。
红波总 00:02:08 空间不大了，有些东西在中间都已经掉了...

人工修订:
红波总 00:01:00 ...你呈现上来的，长名单短名单，基本上是这么选出来的，最后可能评议的空间就已经不大了，有些东西在中间都已经掉了...
```

注意修订同时做了三件事：
1. 合并跨说话人段落（红波总的两段 + 访谈者的补充）
2. ASR 错字订正（"长的短的"→"长名单短名单"）
3. 时间戳保留上一个红波总发言的开始时间（00:01:00）

**校对启示**：跨说话人合并时，**时间戳继承上游段落的开始时间**，不要创造新的时间戳。

#### 5.6.5 关键错字陷阱：语法通顺的严重失真

李红波访谈暴露一个重要 Worker 盲区："全是男的" → "全是难干成的"。

特征：
- 错识后的句子**语法完全通顺**（"现有的干部全是男的"在字面上是合理陈述）
- 单看该段无法察觉错误
- 必须**结合上下文**（下一句讨论"招博士生""二十来岁新人"）才能反推出性别词在此处不合逻辑
- Worker 在只看当前段时会漏校

**校对启示**：对于语法通顺但语境可疑的句子，Reviewer 应**向前向后各扩展一段**检查语境一致性，不能只在当前段内判断。

### 5.7 某主管访谈数据点补充（2026-04-17）

来源：某主管访谈人工修订 diff（v2 42,119 字节 → 人工 29,469 字节，**删减 30%**）。v2 已是 refine moderate 输出（质量评分 89.8），人工仍删减 30%，再次验证适度模式精简不足。

#### 5.7.1 删减比例对照

三次访谈的删减比例：曹朝勋 40% / 李红波 42% / 某主管 30%（基于已校对稿）。某主管偏低是因为 v2 已经过 refine moderate 处理（删减率 18.2%），叠加后总删减约 **43%**，与前两次一致。

#### 5.7.2 新模式：角色化代称替换

受访者在口语中大量使用第一人称"我"或昵称"老解"指代特定岗位角色，书面读者缺乏上下文时无法消歧。人工修订将其替换为角色描述：

| 原文 | 修订后 | 消歧原因 |
|------|--------|---------|
| "比如说,我要走了,谁来接?" | "比如说,任用支持主管走了,谁来接?" | "我"在此不是泛指，而是特指其岗位 |
| "以后老解那,谁来接?" | "以后干部调配,谁来接?" | "老解"对读者不透明 |
| "我考察期干完了" | "我干部考察干完了" | 补充"干部"二字明确考察类型 |
| "这种知识部未来的人" | "任用支持部未来的人" | ASR 错误 + 角色澄清双重修正 |

**校对启示**：Worker 在适度模式下，当受访者用"我"或昵称指代特定岗位角色且**上下文无法自动消歧**时，应主动用角色描述替换。此操作的前提是 Architect 在上下文指南中已提供说话人的岗位信息。**注意边界**：仅替换指代岗位角色的"我"，不替换表达个人观点的"我"（如"我觉得"保留原样）。

## 六、Worker 常见失败模式

| 失败模式 | 表现 | 预防措施 |
|---------|------|---------|
| 偷懒不校对 | 正文几乎原样保留，只列了变更摘要 | Reviewer 严格评分，<80 分退回 |
| 正文与摘要不一致 | 摘要说改了但正文没改 | Reviewer 抽查核对 |
| 虚构时间戳 | 在分段边界创造原文不存在的时间戳 | Reviewer 校验时间戳连续性 |
| 过度修正 | 删除开场段、改变说话人语气 | 忠实度评分把关 |
| 同音错字方向错误 | 如"趋应为→趋之若鹜"（语义相反） | 人工澄清环节兜底 |
