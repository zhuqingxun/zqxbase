# PRD 触发场景章节：写法与模板

由 create-prd 在 `product_types` 含 `skill` 时按需加载。本文件规定「触发场景」章节的模板、写法规则与自检清单。

## 为什么触发场景属于需求而非实现细节

- **description 是模型决定是否加载该 skill 的唯一信号**。正文写得再好，description 没被匹配上，整个 skill 就等于不存在
- **触发条件写不清 = 需求没定义清楚**，不是事后调优问题。"什么时候该用它、什么时候不该用它"本身就是这个 skill 的边界定义
- **在 PRD 阶段定下来才能成为可验收对象**。触发场景清单是 validate 阶段抽测的输入；PRD 里没有清单，验收就只能拍脑袋

## 章节模板（复制进 PRD 后替换内容）

```markdown
### 触发场景

#### should-trigger（8-10 条）

| # | 用户 query | 场景说明 |
|---|-----------|---------|
| 1 | 「……」 | 用户主动发起，口语表达 |
| 2 | 「……」 | 用户用术语表达同一意图 |
| … | … | … |

#### should-not-trigger（8-10 条）

| # | 用户 query | 为什么不该触发 | 正确去向 |
|---|-----------|--------------|---------|
| 1 | 「……」 | 与本 skill 的动作相似但对象不同 | 应走 X skill |
| … | … | … | … |

#### description 草案

> {一行 description 文本}

字数：{N} 字符（上限 1024）
```

## 写法规则

### should-trigger：写真实 query，不写功能名

- **覆盖不同表达**：同一意图的口语说法、术语说法、缩写、以及显式 slash 调用，各占一定比例
- **覆盖不同入口**：既有用户主动开口的场景，也有"用户正处在某个状态下、顺势该触发"的场景（例如刚跑完上一阶段、产出物已就位时的自然下一步）
- **反模式：把 skill 名当 query**。「跑一下 xxx」这类只算 1 条，用它凑满 8-10 条等于没写——用户不知道 skill 叫什么名字时的说法，才是真正要覆盖的

### should-not-trigger：必须是「近失误」负例

- **判定标准**：这条 query 换个人来写 description，就可能把它误匹配进来。够不上这个标准的不算负例
- 明显无关的（「今天天气怎么样」）不构成负例，**不计入** 8-10 条
- **三类高价值负例**：
  1. **相邻 skill 的地盘**：同一插件内另一个 skill 负责的事（例如 mint 的转录与校对是两个阶段，「把录音转成文字」不该落到校对上）
  2. **同词不同义**：关键词字面命中但语义不同（例如 rpiv-loop 里「查看 handoff 列表」与「创建 handoff」共用 handoff 一词，却是两个 skill）
  3. **范围外的相似动作**：动作像但对象超出本 skill 支持范围（例如 ppt 的评审面向已生成的 deck，「帮我看看这份 Word 排版」不在范围内）

### description 三条硬规则

| 规则 | 说明 | 违反的后果 |
|------|------|-----------|
| 第三人称陈述 | 写「本 skill 做 X」而非「你可以用它做 X」 | 与其他 skill 的 description 形态不一致，匹配质量下降 |
| 「做什么 + 何时用」两段式 | 前半句说能力，后半句给触发条件（「当用户说……时触发」） | 只有能力没有触发条件，模型无从判断该不该加载 |
| 只写触发条件，严禁塞工作流摘要 | 步骤、阶段划分、产出物格式一律留给正文 | 步骤描述会稀释触发匹配信号，长 description 的命中率反而更低 |

## 正反例对照

**第 1 组 — should-trigger 的写法**

| 判定 | 写法 | 理由 |
|------|------|------|
| ❌ 反例 | 「执行 mint 转录功能」 | 用户不会这么说；这是功能名不是 query |
| ✅ 正例 | 「把这个录音转成文字」/「这段会议录音帮我转一下」/「ASR 一下」 | 覆盖口语、场景化、术语三种真实表达 |

**第 2 组 — should-not-trigger 的写法**

| 判定 | 写法 | 理由 |
|------|------|------|
| ❌ 反例 | 「帮我订一张机票」 | 与 skill 领域完全无关，不构成误触发风险，属于凑数 |
| ✅ 正例 | 「帮我把这份 PRD 的结构理一理」（对 rpiv-loop 的 plan-feature 而言） | 字面像规划，实际是文档整理，是真实的近失误 |

**第 3 组 — description 的写法**

| 判定 | 写法 | 理由 |
|------|------|------|
| ❌ 反例 | 「先读取输入目录，再解析 Markdown，然后按主题分页，最后调用渲染器输出 pptx」 | 通篇是工作流步骤，没有一个字在说何时该用 |
| ✅ 正例 | 「从目录或文件一键生成 PPT。当用户提到『生成 PPT』『做 PPT』『创建演示文稿』时触发」 | 前半句说能力，后半句给触发条件 |

## 自检清单（进入 plan 阶段前逐条打勾）

- [ ] should-trigger 满 8-10 条，且不是同一句话的近义改写
- [ ] should-trigger 覆盖了口语 / 术语 / 显式调用三类表达
- [ ] should-trigger 含至少 1 条「顺势触发」（用户没直接开口，但当前状态下该触发）
- [ ] should-not-trigger 满 8-10 条，且每条都能说清「为什么容易被误匹配」
- [ ] should-not-trigger 三类高价值负例（相邻 skill / 同词不同义 / 范围外相似动作）至少各覆盖 1 条
- [ ] 每条 should-not-trigger 都写了「正确去向」
- [ ] description 是第三人称、两段式，且不含任何工作流步骤
- [ ] description 字符数已统计并 ≤ 1024
- [ ] 全章节示例不含私有插件名、真实客户名、机器本地路径
