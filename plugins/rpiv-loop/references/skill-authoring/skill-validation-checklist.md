# skill 产物验收清单

## 使用方式

由 validate 第 0.5 步在 `product_types` 含 `skill` 时分派进入。逐项判定后填入摘要报告的「skill 质量门」小节，格式见第六节。G1-G5 与第三、五节分别对应 DoD 模板 `tools/dod_skill_template.yaml` 的 7 条 `DODS-*` gate；**G6 没有对应的 DODS gate**——它是编写反模式检查项，不是交付门禁，理由见该条下方说明。

**输入判定（先做，再往下走）**：

| PRD 的 `product_types` | 处置 |
|-----------------------|------|
| 含 `skill` | 执行本清单 |
| 含 `code` | 走代码侧验证流程（本清单不适用部分标注「不适用」） |
| 字段缺失 | 按 `[code]` 处理，不执行本清单 |
| 空列表 `[]` | 按 `[code]` 处理，等同字段缺失 |
| 找不到对应 PRD 文件 | 按 `[code]` 处理，并在报告中注明「未找到 PRD，按默认代码产物验证」 |

## 一、通用质量门（全类型必查）

| gate | 判定标准 | 验证手段 |
|------|---------|---------|
| **G1** `DODS-FRONTMATTER`<br>frontmatter 合法性 | `name` 为小写字母 + 连字符且 ≤ 64 字符；`description` 非空且 ≤ 1024 字符；`name` 与目录名的一致性按所在插件既有惯例核对 | Read SKILL.md 前 10 行逐字段比对；字符数用 `wc -m` 对 description 单独统计（注意统计的是字符数不是字节数） |
| **G2** `DODS-DESCRIPTION`<br>description 只含触发条件 | 含「做什么 + 何时用」两段；不含步骤、阶段划分、产出物格式描述 | 把 description 逐句归类为「能力陈述 / 触发条件 / 工作流步骤」，出现第三类即判失败 |
| **G3** `DODS-SIZE`<br>正文行数 < 500 | 硬阈值 500 行 | `awk 'END{print NR}' SKILL.md`——**不要用 `wc -l`**，它按换行符计数，末尾无换行的文件会少算 1 行；超限时用 `git diff --numstat` 区分 preexisting 与本次引入，preexisting 不判失败但须已有 todo 跟踪，本次引入直接判失败 |
| **G4** `DODS-DISCLOSURE`<br>分层 + 引用一层深 | **主判据**：「一层深」指**从 SKILL.md 出发的跳转次数 ≤ 1**——SKILL.md 可以引导去读 `references/<file>.md`（第 1 跳），但该文件内部不得再引导读第三个文件。**目录嵌套层数不受此限**：`references/<子目录>/` 只是组织手段，不构成跳转层级<br>**辅判据**：正文不含只服务单一分支的大段细节 | 主判据**只能人工通读**，不可 grep 化——讲解 reference 拆分策略的文件正文必然大量出现 `references/` 字样，grep 分不清「教学中提到的」与「指示去加载的」，必然产生伪 FAIL；辅判据用 `find <references 目录> -mindepth 2 -type d` 加正文抽查 |
| **G5** `DODS-PATH-NEUTRAL`<br>路径中立 | 无硬编码绝对路径、home 目录、安装位置；资源定位走占位符或相对路径 | 见下方扫描命令 |
| **G6**<br>自引用禁用行号 | 引用本文件或同插件其他文件的位置时，**只用章节名或锚点文本**，不得写「第 N 行」「第 N-M 行」 | `grep -nE '第 [0-9]+(-[0-9]+)? 行' <目标>`，命中后按下方三类判定表逐条归类 |

**G5 扫描命令**（在插件根目录执行，目标替换为本次新增/改动的文件或目录）：

```bash
grep -rnE '([A-Za-z]:[\\/]|/[U]sers/|/[h]ome/[a-z]|~/\.[c]laude/skills/)' <目标路径>
```

判定：无输出（exit 1）为通过；有命中即逐条核对，命中行必须改为占位符或相对路径。

> 命令中 `[U]` `[h]` `[c]` 的字符类写法是**刻意为之**：本文件自身会被同一条扫描覆盖，若写成字面形态，扫描会命中这条示例命令本身，产生无法消解的假阳性。字符类对 grep 的匹配语义完全等价。
>
> 另注意盘符分支必须写成上面那种字符类形式 `[A-Za-z]:[\\/]`，**不要把它写成「盘符字母 + 冒号 + 两个反斜杠」的 ERE 字面形式**——ERE 下双反斜杠匹配不到真实路径里的单个反斜杠，会静默漏过全部 Windows 反斜杠写法。这类失败不报错、只是少命中，比误报危险得多。

**G6 命中后的三类判定**（`grep` 只负责找出所有含行号的行，判定必须人工做）：

| 类型 | 特征 | 例子 | 判定 |
|------|------|------|------|
| **① 自引用** | 指向**本文件或同插件其他文件的当前位置**，随文件增删会失效 | 「复用本文件第 N 行确立的契约」 | **失败**，改为章节名或锚点文本 |
| **② 占位示例** | 指向虚构路径，用于教用户填写格式，不指向任何真实文件 | `path/to/file.py (第 15-45 行)` | 通过 |
| **③ 历史案例引述** | 描述**已不存在的历史状态**，不指向本文件或同插件任何文件的当前位置，因此不会失效 | 「某文件曾写『第 N 行』，后来该章节移到了第 M 行」 | 通过 |

只有 ① 判失败。② 和 ③ 都是**有意保留**的内容，删掉反而损失信息。

> **本文件自身的 G6 自检基准**：对本文件跑上述命令应命中**恰好 2 条**——一条是上方表格里的 ② 占位示例，一条是下方实证案例段落的 ③ 历史案例引述。两条都判通过。这个非零基准是有意的：它同时证明 G6 的扫描命令**不是永远返回空的假门禁**（对照附录防线一「没有反例的自验不算自验」），并给出了 ② 与 ③ 两类的活样本。若某次自检命中数不是 2，说明有人新增了行号引用，需按上表逐条归类。

**G6 为什么单列**：行号引用会随同一文件任何一处增删而自动失效，且**失效毫无征兆**——写下时完全正确，别处改动后就悄悄指向了错误内容。

> **实证案例**（本次改造亲历）：某 SKILL.md 中曾写「复用「AC 逐条证据采集」章节（第 129-131 行）已确立的契约」，该行号在写下的那一刻完全正确。但同一文件稍后在前部插入了 20 行新章节，被引用的章节实际移到了第 149 行，而第 129-131 行变成了「3.7 其他 / 未识别」——**引用悄悄指向了一个语义相反的章节**。越是活跃维护的 skill，这种腐坏越快。改用章节名后，同一文件再怎么增删都不会失效。
>
> **G6 不升格为 DODS gate**：G1-G5 对应官方核心规范，是交付前必须过的门；自引用行号属编写反模式，放编写指引里作检查项即可，`dod_skill_template.yaml` 保持 7 条不变。

## 二、分层验收：先判 skill 类型

通用质量门过完后，按 skill 类型走不同的深度验收路径。

### 判定规则

| 类型 | 判定特征 |
|------|---------|
| **客观可验证类** | 有可断言的产出（生成文件、结构化数据、确定性变换），或捆绑了 scripts |
| **流程编排类** | 产出是自然语言、判断结论或多步协作过程，没有机械断言点 |

### 边界案例

| 案例 | 判定 | 理由 |
|------|------|------|
| 产出一份 Markdown 报告，但内容由模型自由撰写 | 流程编排类 | 文件必然生成，但「内容对不对」无机械断言点，断言文件存在等于没验 |
| 捆绑脚本做格式校验，但主体是访谈式对话收集需求 | **两者都做** | 脚本部分按客观可验证类跑，对话部分按流程编排类走人工清单 |
| 把输入按固定规则重排为固定结构，无自由发挥 | 客观可验证类 | 输入相同则输出必然相同，可直接对照断言 |

### 兜底规则

**拿不准 → 默认走流程编排类的人工清单。** 人工清单不阻塞交付（对应 gate 为非 blocking），而误判为客观可验证类会要求拿出根本不存在的机械断言，导致验收卡死。宽松兜底优先于分类精确。

## 三、客观可验证类 → 轻量 baseline 对照（`DODS-BASELINE`）

对照方法、留档要求与常见陷阱见 `skill-eval-guide.md`。本节只规定验收侧要求：

- 场景数 ≥ 3，且必须是真实场景，不是为验证构造的玩具输入
- baseline 与新版本的原始输出**都要留档**，evidence 指向留档路径而非结论文本
- 结论写进 acceptance.yaml 对应条目的 `evidence` 字段
- 流程编排类 skill 在此项判 `not_applicable`，并在 `notes` 说明「按流程编排类验收，见第四节」

## 四、流程编排类 → 结构化人工清单

对应 DoD 的 `manual_review` 形态 gate：validate **不自动执行**，在报告中列为「人工确认」项。

- [ ] 主路径走通：按 SKILL.md 正文从头执行一遍，无死循环、无指向不存在文件的引用
- [ ] 分支可达：每条分派分支至少走通一次，确认不被前置步骤短路
- [ ] references 可解析：正文引用的每个 references 文件都真实存在且能被读取
- [ ] 边界输入不崩：缺字段、空值、找不到上游文件时有明确兜底行为而非卡死
- [ ] 产出形态符合正文声明：正文说产出什么，实际就产出什么
- [ ] 与既有 skill 无职责重叠：不与同插件其他 skill 抢同一场景

## 五、触发场景抽测（`DODS-TRIGGER`）

- 从 PRD 的 should-trigger 与 should-not-trigger 清单**各抽若干条**（抽测非全量）
- 逐条记录三种结果之一：命中 / 未命中 / 误触发
- **未过条目记入 `notes`，不直接判 failed**——触发匹配受上下文影响，单次未命中不构成质量结论
- PRD 无触发场景章节的存量 skill：判 `not_applicable`，在 notes 说明理由
- 抽测必须在**新会话**执行，同会话内已加载的旧 description 会污染判定

## 六、报告呈现格式

在 validate 摘要报告中插入以下小节，逐条填实际结果：

```markdown
### skill 质量门

| gate | 结果 | 证据 |
|------|------|------|
| DODS-FRONTMATTER | ✓ / ✗ | name={n} 字符, description={m} 字符 |
| DODS-DESCRIPTION | ✓ / ✗ | 逐句归类结论 |
| DODS-SIZE | ✓ / ✗ | awk 计数 = {n}（preexisting 超限时注明 todo 路径） |
| DODS-DISCLOSURE | ✓ / ✗ | 跳转次数人工通读结论 + 目录深度检查输出 |
| DODS-PATH-NEUTRAL | ✓ / ✗ | 扫描命中数 |
| G6 自引用行号 | ✓ / ✗ | grep 命中数及人工判定结论（无对应 DODS gate） |
| DODS-TRIGGER | ✓ / ✗ / N/A | 抽测 {x}/{y} 命中 |
| DODS-BASELINE | ✓ / ✗ / N/A | 留档路径或 not_applicable 理由 |

**skill 类型判定**：客观可验证类 / 流程编排类（判定理由：……）
**人工确认项**：{流程编排类清单的逐条打勾结果}
```

无 `manual_review` 项被跳过时须写「人工确认项：无」，不留空。

## 附录、门禁命令自验规则

**元规则，写给使用本清单的人。** 凡是用于门禁判定的 `grep` / 计数命令，交付前必须用**反例**自验：造一个「应当被抓住」的样本，确认它真的被抓住。

**只验「正常情况不误报」远远不够**——那恰恰是假阴性蒙混过关的标准路径。假阴性的特征是：命令不报错、返回一个看起来合理的数字、结论完全错误。它比误报危险，因为没有任何信号提示你去复查。

### 实证：同一条 diff 判据上连栽四次

本次改造中，用于「统计 diff 删除行」的判据被反复修正，每一版都有人自认已验证：

| # | 写法 | 漏掉了什么 |
|---|------|-----------|
| ① | `grep '^-[^-]'` | 漏掉顶格 Markdown 列表行的删除——被删的行本身以 `-` 开头，diff 前缀加上后成了 `--`，第二字符正是列表符号 |
| ② | （沿用 ①） | 该缺陷式被当成诊断工具，据其假阴性发出过错误结论 |
| ③ | `grep -v '^-version:'` | 漏掉 `-  "version": "X",` 形态——JSON 里有缩进和双引号，不顶格 |
| ④ | `grep -v '^---'` | 连「删除 frontmatter 分隔符」的 `----` 一起排除掉了。删 `---` 后 diff 形态是四个连字符，而破坏 frontmatter 分隔符会让整个文件解析失效，属必须抓到的严重错误。正确写法是 `'^--- '`（带空格），只排 diff 文件头 |

**结论**：`git diff --numstat` 这类结构化输出优于自制正则；必须自制时，先造反例再上岗。

### 附带一条同源教训：单一命令的输出不足以支撑结论

`grep -c '关键词'` 漏写文件名参数时会从空 stdin 读取并返回 `0`，看起来就像「该章节缺失」。任何「某内容不存在」的结论，都要用第二条命令（如 `grep -n '^#' <文件>` 列出全部章节）交叉验证后才能下。
