# 轻量 baseline 对照方法

## 核心思想

**没看过 agent 在无 skill 时怎么失败，就不知道 skill 教的对不对。**

baseline 不是为了打分，是为了证明「这个 skill 确实改变了行为」。少了这一步，"skill 写好了"只是一个信念——产出看起来合理，但可能模型不装这个 skill 也能做到同样水平，也可能 skill 里最费笔墨的那几条约束根本没被执行。

对照的产出是**差异**，不是分数。看到差异才知道：哪几条约束真的生效了、哪几条写了等于没写、哪些场景 skill 反而帮了倒忙。

## 两种 baseline

### 新建 skill：baseline = 无 skill 裸跑

- **取样方式**：在**没有加载该 skill** 的会话里，把同样的输入交给模型，让它自由发挥
- **留档要求**：完整保存裸跑的原始输出（不是摘要、不是「大意是……」），以及所用的输入原文
- **常见误区**：拿"我印象中模型以前做得不好"当 baseline。印象不是证据，必须真跑一次

### 优化现有 skill：baseline = 旧版本

- **取样方式**：先用旧版本跑一遍留档，再换新版本跑同样输入
- **留档要求**：两个版本的原始输出都留，并记录各自的版本号
- **常见误区**：直接拿历史上某次执行的产物当 baseline。历史执行的输入、上下文、模型状态都不同，不构成可比对照

## 操作流程

1. **选场景**：挑 ≥ 3 个**真实场景**——用户真实提过的需求、仓库里真实存在的输入。不用为验证构造的玩具输入，玩具输入既不会暴露边界问题，也证明不了实用价值
2. **跑 baseline 并留档**：按上节方式取样，原始输出存档，记下存档路径
3. **跑新版本**：**同输入、同条件**。变量只允许有一个（有没有 skill / 哪个版本），输入措辞、上下文、附带文件都不能改
4. **逐场景对照记录差异**：按下节表格逐场景填写，写清"差在哪"而不只是"哪个更好"
5. **结论写进 acceptance.yaml**：填进对应 AC 的 `evidence` 字段，指向留档路径 + 关键差异摘要

## 记录格式

| # | 场景 | baseline 表现 | 新版表现 | 差异结论 |
|---|------|--------------|---------|---------|
| 1 | {真实输入的一句话概括} | {具体做了什么、缺了什么} | {具体做了什么、补上了什么} | {哪条约束生效了 / 无差异} |
| 2 | … | … | … | … |
| 3 | … | … | … | … |

**填写要求**：

- 「表现」栏写**可指认的具体事实**（少了哪个章节、格式错在哪、漏判了什么），不写「质量一般」「效果不错」
- 「差异结论」栏允许写「无差异」——无差异是有价值的发现，说明该场景下 skill 没起作用，要么场景选错、要么约束没写到位
- 留档路径写进表格上方或 evidence 字段，保证他人可复核

## 明确不做

以下三项**不在**本方法论范围内。写在这里是为了防止后续被误当成待补功能：

- **触发率自动迭代环**（N 个 query × M 次重复 × K 轮自动调优 description）
- **eval viewer / 可视化面板**
- **benchmark 聚合与跨版本打分排行**

理由：本方法论的目标是"证明行为改变了"，不是"建一套评测基础设施"。上述三项的建设成本远高于它们在单插件迭代中的收益。

## 常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|---------|
| 同会话内改完 skill 直接对照 | 旧指引仍在上下文里，验的不是新行为 | **必须新会话**跑新版本；skill 经目录加载时尤其如此 |
| baseline 只跑 1 个场景 | 差异可能来自模型输出的随机性，不是 skill 的功劳 | ≥ 3 个场景，且尽量覆盖不同类型的输入 |
| 只记结论不留原始输出 | 无法复核，evidence 不成立，验收时等同于没做 | 原始输出落盘存档，evidence 指向路径 |
| 拿「感觉更好」当证据 | 不可复核、不可反驳，退化成主观印象 | evidence 必须能指向具体差异（多了哪节、修正了哪个错误） |
| 换 skill 的同时改了输入措辞 | 两个变量同时变，差异归因不成立 | 严格同输入同条件，一次只变一个变量 |
